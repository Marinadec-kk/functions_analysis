# Сравнение скриптов: 1_parsing.py vs document_parser.py

Этот документ сравнивает старую версию скрипта (`pre_ref/1_parsing.py`) и новую, переработанную версию (`pipeline/document_parser.py`).

## 1. Общие функции и цели

Оба скрипта преследуют одну и ту же основную цель: автоматизировать извлечение данных из юридических документов. Их общая функциональность включает:

- **Чтение документов**: Оба способны обрабатывать файлы `.docx` и `.doc`.
- **Использование AI**: Оба отправляют часть текста документа в AI-модель (OpenAI-совместимую) для извлечения полного наименования государственного органа.
- **Извлечение функций**: Оба скрипта ищут в документе раздел "Функции" и извлекают из него список текстовых параграфов.
- **Очистка текста**: Применяют регулярные выражения для удаления из текста функций юридических сносок, примечаний и другого "мусора".
- **Создание аббревиатуры**: Генерируют короткое сокращение из названия госоргана для использования в качестве идентификатора.
- **Определение иерархии**: Пытаются разделить полное наименование госоргана на основное и вышестоящее.

## 2. Ключевые различия

Несмотря на общие цели, подходы к реализации кардинально различаются. Новый скрипт (`document_parser.py`) является значительным шагом вперед с точки зрения архитектуры, надежности и удобства использования.

| Критерий | `pre_ref/1_parsing.py` (Старый) | `pipeline/document_parser.py` (Новый) |
| :--- | :--- | :--- |
| **Архитектура** | **Монолитное приложение** с GUI. Логика и интерфейс смешаны. | **Модульный компонент** пайплайна. Четкое разделение функций. |
| **Интерфейс** | Графический интерфейс на **Tkinter**. | **Командная строка (CLI)**. Использует `tqdm` для прогресс-бара. |
| **Платформа** | **Только Windows**. Зависит от `win32com` для чтения `.doc`. | **Кроссплатформенный** (Linux, macOS, Windows). Использует **LibreOffice** для конвертации `.doc`. |
| **Конфигурация** | Через поля в GUI. Жестко привязана к интерфейсу. | Через внешний **словарь `config`**. Гибко и легко настраивается. |
| **Выходной формат** | Кастомный отчет, сохраняемый в `.xlsx`. | **Pandas DataFrame**, сохраняемый в `.xlsx`. Более стандартный и мощный подход. |
| **Код и стиль** | Процедурный стиль, большой класс `ParserApp`. Отсутствие аннотаций типов. | Функциональный подход, небольшие, чистые функции. **Аннотации типов**, PEP8. |
| **Обработка ошибок** | Базовая, в основном `try-except` вокруг больших блоков. | Более детальная. **Структурированное логирование** (`logging`), явные статусы возврата от функций. |
| **Надежность** | Менее надежен. Остановка GUI может привести к потере данных. | Более надежен. Четкий жизненный цикл, лучшая обработка исключений. |
| **Зависимости** | `tkinter`, `win32com`, `requests`. | `pandas`, `python-docx`, `openai`, `httpx`, `tqdm`. Более современный стек. |
| **Парсинг иерархии** | Реализован внутри функции `_parse_full_go_name`. | Выделен в отдельную, тестируемую функцию `parse_government_hierarchy`. |

## 3. Вывод

`pipeline/document_parser.py` — это полная и качественная переработка исходного скрипта. Он решает ключевые проблемы старой версии:

- **Устранена привязка к Windows**, что делает решение универсальным.
- **Архитектура стала модульной**, что позволяет легко изменять, тестировать и повторно использовать код.
- **Повышена надежность и удобство отладки** за счет логирования и лучшей обработки ошибок.
- **Код стал чище, читаемее и соответствует современным стандартам** разработки на Python.

Переход от `1_parsing.py` к `document_parser.py` является примером успешного рефакторинга, который превратил прототип с GUI в надежный и гибкий компонент для конвейерной обработки данных.
